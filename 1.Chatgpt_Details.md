# 10. AI Orchestrator

Don't connect every service directly to an LLM.

Create:

```text
                AI ORCHESTRATOR
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   Explanation     Vocabulary      Quiz
      Agent          Agent          Agent
        │              │              │
        └──────────────┼──────────────┘
                       │
                 Model Router
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
          Local LLM          OpenAI
```

The **Model Router** decides which model should handle the request.

For example:

| Task                  | Model                 |
| --------------------- | --------------------- |
| Word definition       | Dictionary            |
| POS                   | NLP                   |
| Lemmatization         | NLP                   |
| Simple explanation    | Local LLM             |
| Grammar explanation   | Local LLM             |
| Difficult explanation | Larger LLM            |
| Quiz generation       | Local LLM             |
| Translation           | Translation model     |
| Embeddings            | Local embedding model |

This keeps your operating cost low.

Why do we need hugging face models?

You **don't necessarily need Hugging Face models**. I included Hugging Face because it gives you access to many open-source NLP/AI models, but for your first version, you can build the app without it.

### Think of the stack this way

**Hugging Face is not a model.** It is mainly an ecosystem/hub for models, datasets, and libraries.

For your application:

| Requirement           | Do you need Hugging Face? | Alternative                    |
| --------------------- | ------------------------- | ------------------------------ |
| Dictionary definition | ❌                         | WordNet / dictionary API       |
| Word pronunciation    | ❌                         | Dictionary data                |
| Lemmatization         | ❌                         | spaCy                          |
| POS tagging           | ❌                         | spaCy                          |
| Sentence splitting    | ❌                         | spaCy                          |
| AI explanation        | ❌                         | Ollama + Qwen/Llama            |
| AI-generated examples | ❌                         | Ollama                         |
| Translation           | ❌                         | Translation API / local model  |
| Embeddings            | Maybe                     | Ollama / sentence-transformers |
| OCR                   | Maybe                     | Tesseract / PaddleOCR          |
| Semantic search       | ❌                         | pgvector + embeddings          |

### Where Hugging Face becomes useful

Suppose later you want a specialized model for:

> "Detect whether this sentence is B1, B2, C1 or C2 English."

You might find an appropriate pretrained model on Hugging Face.

Or:

> "Generate high-quality sentence embeddings."

You might use a `sentence-transformers` model.

Or:

> "Run OCR on newspaper screenshots."

You might choose a model such as a document/OCR model from the Hugging Face ecosystem.

Then it becomes useful.

### One important distinction

You could have:

```text
Hugging Face
     │
     ├── Model repository
     ├── Dataset repository
     └── ML libraries
```

while:

```text
Ollama
```

They aren't really competitors.

For your **MVP**, I would deliberately **remove Hugging Face from the core architecture**.

I'd use:

**FastAPI + PostgreSQL + pgvector + spaCy + WordNet/dictionary + Ollama + Qwen + React**

and only introduce Hugging Face when we identify a specific NLP/ML problem that needs a particular model.
